# Task brief — Keep Hermes responsive while Studio renders

**Status:** Proposed — not shipped behavior. Product requirements and pilot permissions clarified with Adam on 2026-11-23. Architecture and pilot targets are proposed and were revised after an independent review the same day. The [idea queue](../future-improvements.md#q7--hermes-availability-during-studio-work) and beta stability gates govern sequencing.

## Problem and required outcome

Adam reports that after sending a Studio job to Hermes on WhatsApp, the same chat becomes hard to use until the job completes. A follow-up like “האם סיימת?” appears to interrupt work, get a reply, and then let work resume. The interruption point and whether the renderer itself stopped remain unverified.

The same WhatsApp chat must stay useful while Studio works. Idle conversation uses the strongest configured local model. During background work, Hermes stays available through a smaller local model for ordinary conversation and verified tools. The strong model plans and supervises work assigned to suitable workers. Requests that require the strong model are saved and completed when it can serve them. Hermes should handle routine permitted work independently. The pilot's permissions and notification policy are settled below. Broader rules for when to involve Adam stay in a parallel workstream.

Adam's measurable goal after two weeks of daily use: he never checks manually whether a render finished, and every "after this, do X" request runs without a reminder. His pain points, in order, are checking whether work finished, remembering the next task, and waiting to ask unrelated questions.

| Example from Adam | Expected behavior in the same chat |
| --- | --- |
| “מה ההתקדמות בעבודה והאם יש צפי לסיום?” | Reply with the current recorded stage, when it last advanced, and an estimated range when measured comparable work supports one. Report unavailable or stale estimates plainly. The renderer keeps working. |
| “אחרי שתסיים את המשימה הזו תבצע גם X” | Save X with a stable task ID, a link to the referenced task, and a visible reason if it is waiting for the earlier task, a plan, a supported executor, capacity, or approval. Confirm after durable acceptance. Resolve ambiguous references before dispatch. |
| The earlier task fails or needs help | Explain the blocker and what Adam can supply or do. Ask whether to continue solving the first task or start X. X waits until Adam changes the dependency or the first task succeeds. If Adam chooses X, retain the first task and its evidence. Release X only if its inputs are available and it passes normal admission. |
| “מה מזג האוויר בתל אביב?” | While rendering continues, the small model uses an authorized read-only weather tool and answers with the location, observation or forecast time, and source. It reports tool failure or missing data truthfully. The provider receives only the necessary lookup fields, such as location and time. |
| A request that needs strong reasoning | Acknowledge and save it in the same chat. Answer when the strong route is healthy and can be admitted safely, then deliver the answer to that chat. |

**Single-GPU scheduling.** Adam wants the strong model to plan before handing off GPU work, and to review or replan at useful checkpoints when the GPU is free. During the lease, verified smaller workers can execute and review defined substeps using prewritten skills and loops. Continuous strong-model inference during an exclusive Studio render requires separate compute. Proposed scheduling default is to serve pending strong-only requests at the first safe GPU boundary, even if compatible CPU work continues. Resume normal strong chat when executable background work clears. Tasks waiting for human input, a dependency, or an unsupported executor should not keep the conversation in background mode indefinitely.

| Evidence | What it tells us |

An ordinary follow-up can be queued and interrupt the active agent turn. Environment or profile settings can override it. Verify the running gateway's effective mode using a synthetic reproduction. In this source, `interrupt` also drops queued messages on a gateway restart, while `queue` and `steer` keep them. |
| Hermes `agent/agent_runtime_helpers.py` and `agent/agent_init.py`, the inspected local Hermes config, and Imperium [`hermes_model_watcher.py`](../../local_model_router/service/hermes_model_watcher.py) | **Likely cause of the held chat (source inspection, not reproduced).** During a Studio lease, Imperium answers Hermes with `503 gpu_leased_by_studio` and `Retry-After: 120` (`STUDIO_LEASE_RETRY_AFTER`). Hermes's outer conversation loop honors `Retry-After`. The inspected config has `api_max_retries: 3` and no fallback provider. A turn that needs inference after Studio claims the GPU, including the post-tool turn that should acknowledge the launch, can therefore be held for several minutes. Under `interrupt`, a follow-up preempts that held turn. Measure this in stage 1 before attributing the symptom to busy mode alone. |
| Installed Studio skill and Hermes `tools/terminal_tool.py`, `tools/terminal_tool_background.py`, and `gateway/run_notifications.py` | The skill already asks for a long timeout, and qualifying terminal calls can be promoted to a background process. Verify that the originating Hermes turn actually ends. Automatic timeout promotion enables a completion notification that can wake a new agent turn and wait behind other work. |
| Imperium [`service/app.py`](../../local_model_router/service/app.py), [`hermes_model_watcher.py`](../../local_model_router/service/hermes_model_watcher.py), and [`BackendManager`](../../local_model_router/helpers/llama_cpp_manager.py) | Managed stop drains accepted model requests. During the lease both the CPU and strong connections returned `503 gpu_leased_by_studio` before forwarding. A second Hermes connection also changes contracts. `HarnessProfiles.resolve` then requires an explicit connection name, so existing unnamed Hermes requests fail. The repo `AGENTS.md` allows several named connections only for Agent Zero. The current stop reason and per-slot coordination do not provide restart-safe ownership of the whole GPU. |
| Local Studio source, `skill/imperium-studio/scripts/studio.py` | The installed script matched `08d1f6f` during inspection. Local Studio `main` at `0ec9edb` has watchdog recovery fixes verified with simulated services. The current video pipeline can hold one lease across several GPU stages and then finalize on CPU. Renderer exit or lease release can precede completion of the whole job. Current history polling alone does not establish a trustworthy ETA. |
| Fleet [configuration example](../../conf/llama_cpp_servers.example.yaml) and [subprocess launcher](../../local_model_router/helpers/backends/subprocess_backend.py) | The example utility worker is disabled and refers to a separate Docker worker. Verify an actual Windows CPU-only serving path, including device selection and observed VRAM use. The Windows launcher omits the GPU-layer flag when the configured value is zero, so the example setting alone is insufficient evidence of placement. |

Record the actual strong-model identity and serving profile when reproducing. The strong and small roles are operator-configured and do not depend on a particular model name.

## Proposed behavior and ownership

| Owner | Responsibility |
| --- | --- |
| **Hermes** | Own the conversation, authorization, commitment capture in מעקב אדם, execution records, dependencies and result delivery. Save a high-level plan with typed worker steps and declared resource needs. The strong model can propose or review the plan. Application code validates the plan and owns dispatch, dependency completion, and retry decisions. Acknowledge and release the launch turn even if the job immediately claims the GPU. Keep authorized typed status and intake available without inference, and deliver recorded completion and the result through the originating chat without requiring another model turn. |
| **Studio** | Execute one exclusive GPU workload at a time. Own rendering, CPU finalization, factual progress events, artifact verification, and reconciliation of owned renderer attempts. Accept an idempotent typed dispatch from Hermes and report the job, attempt and lease generation. Send the start message, with job ID and ETA or "unknown", before acquiring the lease, using the existing WhatsApp delivery path. The launch acknowledgment then never depends on inference after the GPU is claimed. Keep overall task outcome tied to completion of required finalization and artifact checks. |
| **Imperium** | Own local inference routing and shared GPU capacity admission. Reuse slot drain and verified model restore. Give Studio an exclusive, owner-bound reservation before the renderer starts, covering the period from drain through renderer exit. Today the lease lives only in process memory, and `BackendManager.start_slot` clears it unconditionally. Persist the reservation, and refuse a start while it is held. Scope the Hermes ingress gate to the leased slot. During a lease, return a code that sends Hermes straight to its standby route instead of three 120-second retries. Every competing GPU start, watcher swap, or restart must consult the same ownership check, including after Imperium restarts. Keep admission closed if ownership or process exit is uncertain and surface a recovery action. |

**Small-model chat and workers.** Prewarm an approved small text and tool-capable slot with verified zero GPU offload and bounded CPU, memory, context, and concurrency. Use a distinct verified local inference route and enough authorized context to continue the same conversation. Indicate background mode without overwriting the saved strong session selection. Route to the small model only by an application-code rule Adam set on 2026-11-23. A request goes to the small model only if it maps to a registered, versioned skill or loop, or to an allowlisted read-only tool such as status, intake or weather, and it completes in a few bounded steps without a planning phase. Everything else is saved for the strong model. Model confidence does not widen this allowlist. Save turns that exceed the available safe context. Pass low-risk tool calls through typed, validated adapters with their own scope and failure handling. Interactive traffic has a reserved capacity budget. Admit independent CPU workers only from measured remaining headroom, and give them only the inputs and tools the plan requires. If inference is down, explicit status, supported typed intake, and completion delivery keep working.

**Small-worker skills and review loops.** Start with one approved, versioned CPU skill for a bounded step, such as a factual check of a Studio run manifest against its recorded milestones. Give the worker a typed brief, minimum inputs, allowed tools, resource and retry budget, and an explicit verification rubric. Each run records checks, evidence, result, and any uncertainty. The scheduler enforces the limits, rejects invalid output, and queues uncertain or consequential findings for strong review or human input under the relevant policy. Require a known passing example, a known failing example, a timeout, and a deceptive or incomplete input before enabling the skill. A claim of completion from a model cannot clear a required artifact check.

**Job and lease behavior.** Record `queued`, `blocked`, `starting`, `running`, `succeeded`, `failed`, `canceled`, and recovery state with timestamps and factual stage updates. For dependent tasks, store the task and success dependency before acknowledgment. After verified success of the full parent task, admit the child once. On an unresolved failure or blocker that needs Adam, keep the child pending and send one clear choice with the evidence and the smallest useful intervention. Persist Adam's response against the current task and attempt. An explicit decision can continue the parent or release the child when required inputs exist. Use source-event idempotency and fenced attempts for acquire, release, completion, and cancel. Reconcile ownership before retrying. Bind status, control, and delivery to the authorized originating chat. Record notification and artifact delivery separately, and surface ambiguous or failed delivery with a recovery path. Keep only safe identifiers, stage, timing and reason codes in diagnostics. Job payloads and artifacts stay in their authorized local stores.

**Scheduling.** Dispatch only dependency-ready work with a permitted executor and verified resource budget. Start with ordered admission within each resource class and allow compatible CPU work to overlap a GPU job. Apply bounded fairness to pending strong requests and consolidation to planning checkpoints, so a render backlog cannot hold the strong route indefinitely or add a GPU reload between every small step. Verify standby responsiveness before draining the strong slot for the pilot. Leave the active render running if standby fails mid-job. After release, honor a preexisting manual stop and apply any eligible change to the strong selection made during the lease. Queue overflow, blocked work, or insufficient capacity must be visible in the chat.

**Pilot permissions (decided by Adam, 2026-11-23).** Without asking, Hermes may:
- retry a failed render once with the same settings
- start the next GPU job when its dependency and inputs are satisfied
- deliver artifacts to the originating chat
- call an approved read-only external lookup, such as weather
- downshift a turn to the small model under the routing rule above

Further retries, changed settings, and actions outside this list stay pending for Adam.

**Notification policy (decided by Adam, 2026-11-23).** Quiet by default. Send one start message: goal understood, tasks split, work started, and an ETA or "unknown". After that, write only to report a failure or blocker, to confirm durable acceptance of a new task, to answer Adam's own messages, or to deliver the result. Do not stream progress. Status is available on request.

**Parallel autonomy workstream.** Define the broader human-in-the-loop policy separately, with the task contract carrying requested scope, permitted actions, reason for approval, and a pause or cancellation control. The pilot may accept and plan work, and run the permitted actions above. An action outside that authority stays pending for review. The policy workstream decides which external actions, resource or cost thresholds, visibility, retries, and priority changes Hermes may handle without asking. A model's confidence cannot grant permission. The main pilot can validate overlap against fake adapters before these broader rules are settled.

**Trade-off.** A prewarmed CPU model reserves RAM and can compete with rendering for CPU time, particularly during setup and encoding. If same-machine measurements fail the responsiveness or render-cost budget, start with detached jobs and deterministic status, and test a smaller CPU model or separately verified local device before claiming conversational availability. This keeps the user in control of local work, its resource use, and the resulting artifacts through the same chat.

## Path to implementation

| Stage and owner | Work and evidence required to advance |
| --- | --- |
| **1. Baseline — Hermes and Studio** | Record installed and running versions, effective busy mode, slot identities, and the Studio entry point. Use a slow fake tool while the strong slot is healthy to isolate turn preemption. With a free turn, reproduce the route gate during a simulated lease. With a fake Studio that claims the GPU immediately after submission, measure how long the launch turn is held by `503` / `Retry-After` retries, and whether the acknowledgment arrives. Timestamp inbound, durable acceptance, turn return, renderer progress and response without saving message bodies. |
| **2. Durable intake and recovery — Hermes** | Capture X as an idempotent commitment in מעקב אדם, linked to its execution record. Prove the smallest Hermes Kanban adapter with a fake Studio worker, one dependency edge, a duplicate inbound race, and a failed-parent decision issued from the original chat. Prove a restart between create, subscribe and acknowledgment. Make immediate reservation safe even before a post-tool turn could run. With inference off and another turn busy, test authorized status, supported typed intake and direct completion including artifact failure recovery. Keep generic auto-dispatch off for this proof. |
| **3. Capacity and role routing — Imperium and Studio** | Reuse the slot drain under exclusive restart-safe GPU ownership. Test all competing launch paths and stale attempts with fakes. Prove the exact authenticated small and strong connections against the same lease. Then measure CPU, RAM, GPU placement, render cost, chat latency, and restore time on Windows with an approved short render. Revalidate the configured strong identity and turn after release. |
| **4. Planning, review and scoped tools — Hermes** | Test a strong plan that produces one Studio step, an independent CPU review loop and one explicit dependent step. Run a checkpoint after verified release. Give the standby chat the scoped status, intake and weather tools. Validate the effective tool schema and reject unauthorized calls at the action boundary even after reconnect. Treat an existing weather plugin as a candidate, or use a narrow approved provider adapter. No prior weather tool was verified on this WhatsApp runtime. |
| **5. Phone canary and rollback — Hermes, Studio and Imperium** | In an approved test chat, exercise Adam's three examples plus a strong-needed request during real progress. Confirm usable replies and continued renderer progress, surviving queue state, end-to-end artifact delivery, and a successful strong checkpoint and return to idle chat. Test a separate parent failure and Adam's two recovery choices. Make the pilot opt-in and verify rollback that reconciles accepted work. Keep all evidence versioned and sanitized. |

Proposed sequencing for review: deterministic start and completion messages plus durable "after this" intake (stages 1–2 and the lease ownership in stage 3) meet Adam's two success measures without a conversational small model. The small-model standby lane can follow if waiting to ask questions during renders still hurts after that.

Run the policy workstream in parallel with stages 1–3. Its review packet should identify permissions for each pilot action, what evidence triggers escalation, and what Adam can approve or stop in chat. Production dispatch of broader actions waits for that policy decision.

## Acceptance checks

| Test | Passing evidence |
| --- | --- |
| Chat and render overlap | A durable launch acknowledgment, natural-language status, explicit model-free status, a useful chat answer in Hebrew, and one sourced Tel Aviv weather answer arrive in the same chat while the renderer continues. Stage matches recorded evidence and ETA is a calibrated range or explicitly unknown. Verify actual artifact delivery separately from the completion text. |
| Quiet by default and success measures | With a fake Studio that claims the GPU at submission, the start message (job ID, ETA or "unknown") still arrives within 5 s. A render without failure produces at most two unprompted messages: start and result. Over the two-week canary, Adam sends no manual "did it finish?" check, and every recorded "after this" commitment runs or reports a blocker without a reminder. |
| Named inference paths | With the same GPU reservation active, the actual authenticated Hermes fallback connection serves a useful reply on the verified CPU worker. An explicit strong-only request through the pinned connection returns a structured busy response with no model forwarding. Confirm the CPU slot identity, the unchanged strong pin, zero upstream inference calls and no competing GPU start. Verify the pinned route serves the expected model after release. Extend [the existing Studio lease test](../../tests/test_gpu_swap_api.py) to exercise both paths together. The test fails today, because the ingress gate rejects every Hermes connection. Existing unnamed Hermes requests keep working after a second connection is added. |
| Response and compute budget | Proposed pilot thresholds on the reference Windows machine: durable launch acknowledgment and model-free status within 5 s, and first usable small-model reply within 15 s, at p95 over at least 20 samples per path in controlled runs. Compare median time for the same render with and without this feature under a stated concurrent workload. Proposed ceiling is 15% extra render time. Report these separately from the [strong-promotion budget](../adr/0009-five-second-promote-budget.md). |
| Dependency, deduplication and fairness | X appears immediately as one commitment in מעקב אדם with a stable ID and a linked execution record, stays waiting through GPU release and CPU finalization of the parent, then runs once after verified completion. Concurrent duplicate intake still creates one task. Queue-full is visible. A strong-only request waits through the active lease and completes at an admitted boundary with background work still queued. |
| Human intervention after failure | Inject both a missing input and a failed parent. Hermes sends one clear issue with the evidence, offers to continue the first task or start X, and records the decision against the current attempt. Test each answer. An authorized override only releases X if its inputs and permissions are valid. |
| Skill and role quality | Verify the strong model produced the plan and ran a review checkpoint after release. A small worker runs a bounded validation skill and reports actual failed checks. Inject invalid output and an out-of-scope tool call. Both are held or rejected, and small worker load leaves enough capacity for chat. |
| Ownership and recovery | Race Studio acquisition against manual start, start-all, watcher swap and auto-restart. Inject worker/router/gateway loss, lost acknowledgments and ambiguous renderer ownership. Verified active GPU ownership excludes competing starts. Recovery neither double-launches a job nor clears ownership on a memory reading alone. Strong availability returns only after valid release and health/model verification. |
| Degraded behavior and boundaries | CPU fallback unavailable, overloaded, or incapable yields truthful status or wait. Authorized queue commands and completion delivery work with inference unavailable. A turn reaches the small model only under the allowlist routing rule, never to a cloud model without the user's selection. A request outside the allowlist waits for the strong model. An unrelated chat cannot inspect, cancel or receive a job. An explicit authorized cancel is the only chat action that intentionally stops a render. Diagnostics contain reason codes and no prompt bodies or secrets. |
