Imperium - מפת דרך ל-1.0 Beta

מסמך חי לרצף העבודה עד 1.0 beta. חוזה התוצאות נשאר ב־ GOALS.md; ראיות השערים ב־ docs/1.0-beta-evidence.md. יעד הבטא: התקנה → השלמה מקומית → חיבור לקוח → התאוששות מודרכת, בלי עריכת YAML.

החלטת מוצר

1.0 Beta יהיה מוצר עצמאי: Imperium. לא "תוסף ל-Agent Zero", לא "LangFlow clone", ולא מערכת שמבקשת מהמשתמש להבין Docker, llama.cpp, YAML או קוד.

LangGraph, LangFlow, ו־orchestration מתקדם נשארים אחרי שערי הכניסה מחדש ב־future-orchestration.md. בטא 1.0 לא דורשת runner של רשת סוכנים.

יעד בטא (GOALS)

  • התקנה/הפעלה אחת בלי YAML ידני.
  • בחירת מודל אוטומטית או מומלצת.
  • השלמת chat מקומית ראשונה.
  • חיבור לקוח/harness אחד לפחות.
  • התאוששות מודרכת; אין prompt bodies בטלמטריה.

החלטת מודלים וחבילה

מאמצים את ההפרדה של Agent Zero ברמת העיקרון, אבל לא מעתיקים אותה אחד לאחד. ב-Imperium הישות המרכזית היא חבילה: persona, loop, ticket, מודל, כלי הרצה, מגבלות משאבים, DOX, artifacts וכללי עצירה.

תפקיד אחריות ב-Imperium לא באחריותו
Chat / Planner שיחה עם המשתמש, הבנת מטרה, שאלות הבהרה, תכנון חבילות, אישור לפני הרצה. מעקב טכני שוטף אחרי heartbeats והרצת subprocesses.
Utility / Router בדיקות readiness, סיכום הקשר, חילוץ משימות, מילוי metadata, תעדוף queue ומעקב רקע. החלטות מוצר/ארכיטקטורה כבדות או כתיבת קוד מורכבת.
Runner קוד קשיח שמריץ חבילה, פותח process, מגביל concurrency, שומר artifacts ומדווח status. Reasoning. runner לא צריך להיות מודל; הוא צריך להיות מתזמן אמין.
PI Code Worker הרצת משימות קוד דרך PI עם DOX, persona, loop, allowed paths ובדיקות הצלחה. ניהול גלובלי של כל המערכת.
Embedding אינדוקס וזיכרון מקומי אם יש צורך. תכנון, שיחה, או ביצוע משימות.

החלטת beta: המשתמש מדבר עם Chat/Planner חזק. Utility קטן עובד ברקע רק להכנת חבילה ולמעקב קל. אחרי אישור המשתמש, runner קשיח מפעיל חבילות; למשימות קוד הוא מפעיל PI.

Package V0 מינימלי

זה ה-contract הראשון בין planner, utility, runner והדשבורד. אין פה DSL חדש: JSON פשוט שה-orchestrator יכול לשמור ולהציג. 

{
  "persona": "local-coder",
  "loop": "code_fix_verify",
  "ticket_id": "ticket-123",
  "model_role": "utility",
  "runner": "pi-subprocess",
  "tools": ["pi", "pytest"],
  "allowed_paths": ["local_model_router/", "tests/"],
  "success_checks": ["python -m pytest tests/ -q"],
  "resource_limits": {"max_parallel": 1},
  "artifacts_dir": "plans/.../tickets/.../artifacts"
}

ה-Utility רשאי להציע או להשלים חבילה, אבל לא להריץ אותה. ה-Runner מריץ רק חבילה מאושרת ושומר סטטוס, stdout/stderr, artifacts ו-DOX report.

מה כבר קיים במוצר

  • OpenAI-compatible router: /v1/models, /v1/chat/completions.
  • Routing מוסבר: aliases, auto, strategies, analytics.
  • Dashboard קיים: Home, Chat, Models, Connections, Fleet, Routing ו-Diagnostics.
  • Cookbook סורק GGUF ומחשב התאמה ל-VRAM.
  • Fleet control קיים אך כבוי כברירת מחדל.
  • Agent Library מובנה. API ה-Orchestrator הישן נשמר כתאימות deprecated ומוסתר מה-UI.
  • התקנת Windows עצמאית, managed llama.cpp ו-Setup מונחה בן שישה שלבים.
  • בדיקות hermetic רחבות.

מה עדיין חסר לבטא אמיתית

  • אימות clean-machine רחב על NVIDIA, AMD, Intel ו-CPU בלבד (ראו evidence).
  • update / repair / rollback / uninstall release-tested על RC.
  • Browser smoke לדשבורד בשתי השפות ובשתי ערכות הנושא.
  • מטריצת גרסאות harness מול installed + current stable.
  • Deferred אחרי beta: runner לרשת סוכנים / orchestration חדש.

תוכנית עבודה אחרי בטא: llama.cpp workers + AirLLM deep-local

כיוון ניסויי: llama.cpp נשאר מנוע העבודה המהיר למודלים קטנים ולמשימות מקביליות; AirLLM נבחן כנתיב מקומי קר ואיטי למודל גדול שאינו נכנס לזיכרון הרגיל. AirLLM אינו מחליף את מסלול warm weak → hot strong ואינו נדרש לבטא. 

Hermes / OpenAI client
        |
        v
Imperium :9000
  |-- llama.cpp slots: utility / coder / scribe / embeddings
  `-- explicit airllm/deep-local
        `-- loopback AirLLM sidecar :8092 --> pinned HF model

רצף העבודה

  1. Baseline קודם: למדוד מודל גדול ב־llama.cpp עם partial GPU offload. אם הוא נותן איכות וזמן שימושיים לצד slots קטנים, עוצרים כאן ולא מוסיפים runtime נוסף.
  2. מעבדת AirLLM מבודדת: סביבה נפרדת וגרסה מוצמדת; מודל ו־revision מורשים מראש; הכנת שכבות מפורשת; loopback + bearer auth; ללא הורדת מודל או מחיקת checkpoint מתוך בקשת chat.
  3. Sidecar מינימלי: לממש ב־scripts/airllm_sidecar.py רק /health, /v1/models ו־non-streaming /v1/chat/completions. בקשה פעילה אחת, פלט התחלתי של 64–128 tokens, וללא tools, vision או JSON mode.
  4. חיבור מפורש ל־Imperium: להוסיף upstream כבוי כברירת מחדל ב־conf/upstreams.yaml ולפנות אליו בשם airllm/deep-local. לא להצהיר בתחילה על models: ולא לאפשר auto-routing אליו. להשתמש ב־openai_compatible הקיים ולא להחזיר את רישום AirLLM הישן שלא שירת בקשות.
  5. Timeout נקודתי: להוסיף timeout_seconds לכל upstream ב־local_model_router/upstreams/registry.py ולהשתמש בו ב־ service/app.py. אין להגדיל את ה־timeout הגלובלי של כל הספקים.
  6. דו-קיום מדוד: להפעיל slots קטנים בהדרגה, לשמור תקציב VRAM קבוע ל־AirLLM, ולהגדיל local concurrency רק אחרי smoke ללא OOM. מנהל משאבי GPU כללי נוסף רק אם מדידה מוכיחה שהתקציב הקבוע אינו מספיק.

מפת רכיבים

נתיב שימוש בתוכנית מצב

local_model_router/upstreams/registry.py timeout פר-upstream והגדרות admission קיימות. הרחבה קטנה מתוכננת.

local_model_router/service/fleet_manager.py תור נפרד upstream:airllm עם active/queue מוגבלים. קיים.
local_model_router/routing/catalog.py למנוע הנחת resource זול עבור upstream מקומי לפני מודל משאבים מפורש. אין שינוי ב־MVP; AirLLM נשאר מחוץ ל־auto.
scripts/airllm_sidecar.py מעטפת OpenAI דקה מעל מודל AirLLM מוצמד. חדש, רק אם שלב המעבדה עובר.
docs/INTEGRATIONS.md הפעלה, מגבלות ו־curl smoke לאחר שהחיבור קיים. לא לתעד כהתנהגות זמינה לפני implementation.

שער Go / No-Go

  • למדוד prep time, נפח דיסק, TTFT, seconds/token, VRAM/RAM, ביטול והתאוששות.
  • להשוות את אותה חבילת משימות מול llama.cpp partial offload; AirLLM חייב לפתוח מודל/איכות שלא מתקבלים בדרך הפשוטה.
  • שער ניסוי התחלתי: לפחות 0.1 token/s, ללא OOM, ופגיעה של פחות מ־20% ב־p95 של workers קטנים שנשארו פעילים.
  • אם אין שיפור איכות שימושי או שהזמן אינו נסבל, AirLLM נשאר כלי מעבדה ידני ולא נכנס למוצר.
  • מסלול hot strong האינטראקטיבי עדיין חייב לעמוד בתקציב promote של כ־5 שניות; deep-local הוא בחירה מפורשת בלבד.

Hermes נשאר בעל agent loops ופירוק משימות. Imperium אחראי לניתוב, admission, בריאות והסבר ההחלטה; התוכנית אינה מחזירה orchestration מתקדם ל־router core.
